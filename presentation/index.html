О проекте

Координация там, где нет связи

Поисково-спасательные отряды работают в лесу, в поле и в горах — там, где мобильный интернет пропадает на часы. Обычные мессенджеры и карты в таких условиях теряют данные. KuKLA создаётся именно для этого сценария.

⚙️ Backend Redis Pub/Sub, WebSocket-комнаты и Reconnect ▶

Сейчас WebSocket в KuKLA — это просто «эхо-пинг», он не доставляет данные. Задача — сделать его полноценным каналом реального времени.

1
Redis Pub/Sub (издатель/подписчик)

Сервер, приняв новую GPS-точку, «публикует» её в Redis. Другие экземпляры сервера, подписанные на канал, получают сообщение и передают своим клиентам. Это позволяет масштабировать сервер горизонтально.

2
WebSocket-комнаты по search_id

Чтобы не спамить всех клиентов всеми событиями, соединения группируются в комнаты. Клиент подключается к комнате конкретного поиска, и сервер шлёт обновления (GPS-точки, изменения задач) только в неё.

3
Reconnect с экспоненциальной задержкой и джиттером

Критично для нестабильной связи. Вместо попытки каждую секунду интервал растёт (1с, 2с, 4с, 8с…), а случайная задержка не даёт всем клиентам переподключаться одновременно.

📱 Mobile Idempotency, Identity и конфликты ▶

Решаем проблему дублирования данных и потери информации при работе в офлайне.

1
Idempotency keys

Клиент генерирует UUID для каждой операции. Если связь пропала и отправка повторяется, уходит тот же ключ — сервер распознаёт дубликат и не создаёт повторную запись.

2
Device identity

Однозначная идентификация устройства — для безопасности и корректной синхронизации, когда устройством пользуются несколько поисковиков.

3
Обработка конфликтов

Если двое офлайн изменили один объект, нужна стратегия: «последний изменивший побеждает» либо сохранение обеих версий для ручного разрешения координатором.

4
Убрать дефолтные креды

В LoginScreen зашиты логин и пароль searcher@kukla.local. Удобно для разработки, недопустимо в релизе — удаляем.

💻 Frontend Realtime, история трека и кластеризация ▶

Улучшения Desktop-клиента, которые сделают работу штаба удобнее.

1
Подписка на realtime

Сейчас трек обновляется по кнопке. Подключаем клиент к каналу /api/v1/ws, чтобы новые GPS-точки и задачи приходили сразу.

2
История трека за период

API уже поддерживает параметр ?since=. Добавляем в UI выбор периода («за последний час», «за всё время»), чтобы видеть весь маршрут.

3
Кластеризация маркеров

Много точек превращают карту в «кашу». Кластеризация группирует близкие маркеры и раскрывает их по клику — через react-leaflet-cluster и leaflet.markercluster.

🛠️ DevOps Redis, мониторинг и логи ▶

Надёжность и наблюдаемость инфраструктуры.

1
Реактивация Redis

Сервер уже включает Redis в docker-compose, но код его не использует. Настраиваем Redis как брокер сообщений для pub/sub.

2
Мониторинг (Prometheus + Grafana)

Prometheus собирает метрики — запросы в секунду, задержку, память; Grafana визуализирует их в дашбордах.

3
Логи (Loki)

Логи собираются в одном месте вместо ручного обхода контейнеров — их можно фильтровать и искать. Обычно вместе с Promtail.

🧪 QA Тестирование синхронизации и Reconnect ▶

Проверяем, что все механизмы выше действительно работают.

1
Тесты offline/online sync

Сценарии: приложение офлайн, пользователь ставит точки, связь появляется — и данные синхронизируются. Проверяем, что очередь команд сохраняется и обрабатывается правильно.

2
Retry без дублей

Прямая проверка идемпотентности: клиент отправляет точку, не получает подтверждения и отправляет снова. Сервер должен распознать дубликат по ключу.

3
Тесты reconnect

При разрыве соединения клиент переподключается с растущей задержкой и восстанавливает состояние после подключения.
