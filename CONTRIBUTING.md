# Contributing to KuKLA

Спасибо за интерес к KuKLA. / Thank you for your interest in KuKLA.

KuKLA развивается как открытый проект. Мы приветствуем код, тестирование, документацию, дизайн, предложения по архитектуре и практическую обратную связь от поисковых отрядов.

## 🇷🇺 Как участвовать

1. Изучите README и документацию.
2. Проверьте существующие Issues, чтобы не создавать дубликаты.
3. Для ошибки создайте Issue с описанием проблемы, шагами воспроизведения и ожидаемым результатом.
4. Для новой функции сначала опишите задачу и обсудите её в Issue.
5. Для изменений кода создайте отдельную ветку от `main`.
6. Сделайте небольшие, понятные коммиты.
7. Перед Pull Request проверьте сборку и тесты, относящиеся к изменению.
8. Создайте Pull Request и подробно опишите, что изменено и зачем.

### Принципы

- Безопасность важнее скорости разработки.
- Надёжность важнее количества функций.
- Решения должны быть понятны и поддерживаемы.
- Изменения, влияющие на полевую работу, должны по возможности проверяться в реальных или приближенных к реальным сценариях.
- Не добавляйте секреты, реальные персональные данные, реальные координаты поисков и другую чувствительную информацию в репозиторий.

## 🇬🇧 How to contribute

1. Read the README and documentation.
2. Check existing Issues to avoid duplicates.
3. For bugs, open an Issue with the problem, reproduction steps and expected behavior.
4. For new features, describe the use case and discuss it in an Issue first when practical.
5. Create a separate branch from `main` for code changes.
6. Keep commits small and understandable.
7. Run the relevant build and tests before opening a Pull Request.
8. Open a Pull Request explaining what changed and why.

### Principles

- Security comes before development speed.
- Reliability comes before feature count.
- Technical decisions should remain understandable and maintainable.
- Changes affecting field operations should be tested in realistic scenarios whenever possible.
- Never commit secrets, real personal data, real search coordinates or other sensitive information.

## Pull Requests

A good Pull Request should contain:

- a clear title;
- a short explanation of the problem;
- the proposed solution;
- testing performed;
- known limitations or follow-up work.

For substantial architectural changes, please discuss the approach in an Issue before implementation.

## Field feedback

Feedback from searchers and coordinators is especially valuable. If a feature works technically but is inconvenient or unsafe in field conditions, report that explicitly. Operational reality is an important part of KuKLA's requirements.
