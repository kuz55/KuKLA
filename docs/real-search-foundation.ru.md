# Основа для реального поиска (design baseline)

**Статус:** проектная основа, не является юридическим согласованием и не даёт допуска к реальным данным.
Реальная обработка персональных и медицинских сведений (152-ФЗ, при необходимости 323-ФЗ) и взаимодействие
с МВД/МЧС требуют отдельного юридического и операционного одобрения (см. `acceptance/release-approval-checklist.ru.md`).
Документ описывает модель и пробелы; он не утверждает формы отчётности и не разрешает сбор реальных данных.

## 0. Что уже есть в схеме (задел)

- `searches` — жизненный цикл поиска, место инцидента (`incident_lat/lng`), `area`, `started_at/ended_at`.
- `subjects` — карточка пропавшего (без фото/жёсткого удаления, только менеджерский доступ).
- `operational_periods` — операционные периоды/смены (`PLANNED/ACTIVE/CLOSED`, брифинг/дебрифинг).
- `search_sectors` — сектора/зоны: `code`, `status`, `priority`, `geometry jsonb`, `pod`, `notes`.
- `search_teams` — группы с `team_type` `FOOT/VEHICLE/K9/UAV/AIR/OTHER` и `status`.
- `team_members` — состав группы.
- `task_assignments` — связь задача ↔ группа ↔ сектор ↔ операционный период (ключевая сущность назначений).
- `clues`, `witnesses`, `resources`, `checkins` (со статусом `OK/DELAYED/HELP/EMERGENCY`), `notifications`, `gps_points`, `sync_operations`, `hazards`, `evidence`, `emergency_events`.

**Критический пробел:** геометрия хранится как `jsonb`, без PostGIS — нет пространственных запросов
(буферы, пересечения, расчёт покрытия, расстояния). Ролевая модель покрывает только глобальное управление
(`LEADER/COORDINATOR/REGIONAL_MANAGER/...`), а не полевые должности и специализации.

---

## 1. Операционная модель поиска (фазы)

1. **Инициирование** — заявление/сигнал, карточка пропавшего, оценка риска, решение о начале поиска, уведомление МВД/ЕДДС.
2. **Планирование** — рубежи и сектора, назначение групп и специалистов, постановка задач, брифинг, распределение ресурсов.
3. **Проведение** — выдвижение групп, чекины и трекинг, выполнение задач, сбор улик/свидетелей, SOS/эскалация, сводки.
4. **Завершение** — closeout, дебрифинг, неизменяемый архив и replay, аналитика и отчётность (в т.ч. МВД).

Каждая фаза фиксируется в аудите; sensitive-данные скрыты от не-менеджеров.

## 2. Роли и специалисты

### 2.1 Глобальные роли (уже в RBAC) — управление доступом
`SYSTEM_OWNER/SUPERADMIN/SUPERUSER/ADMIN/LEADER/COORDINATOR/REGIONAL_MANAGER/SEARCHER/VIEWER`.
`REGIONAL_MANAGER` — только прямое членство в поиске. Эти роли НЕ описывают полевые должности.

### 2.2 Оперативно-штабной состав (назначается на поиск/период)
- Руководитель поиска (РП/ИД) — единое управление, утверждение плана и отчётов.
- Зам. РП, координатор базы/логистики, связист (радио/телефония), ГИС-специалист/картограф, спец. по БДД и безопасности.

### 2.3 Полевые специалисты (квалификация, не глобальная роль)
- Командир группы (пеший/авто), спасатель-разведчик, кинолог (K9), оператор БПЛА, медик, радист, навигатор,
  опросчик свидетелей, специалист по документированию/уликам, переводчик.
- Квалификация задаётся отдельной сущностью `specialist_qualifications` и связывается с `team_type` и допустимыми задачами.

### 2.4 Взаимодействие (внешние роли/организации)
- Представитель МВД/полиции, МЧС/ЕДДС, координатор волонтёров, представитель семьи.
- Моделируется через существующие `organizations` + `search_organizations` и новую роль взаимодействия.

### 2.5 Предлагаемая сущность квалификаций (черновик)
```sql
CREATE TABLE IF NOT EXISTS specialist_qualifications (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  qualification text NOT NULL,          -- K9, UAV, MEDIC, RADIO, NAVIGATOR, WITNESS_INT, EVIDENCE, ...
  team_type text NOT NULL,              -- ограничение по типу группы
  certified_at timestamptz,
  expires_at timestamptz,
  active boolean NOT NULL DEFAULT true
);
CREATE TABLE IF NOT EXISTS team_roles (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  team_id uuid NOT NULL REFERENCES search_teams(id) ON DELETE CASCADE,
  user_id uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  role text NOT NULL,                   -- LEADER, MEDIC, RADIO, SEARCHER, ...
  PRIMARY KEY(team_id, user_id, role)
);
```
Глобальная роль `users.role` ≠ полевая должность; права на данные по-прежнему определяет `membership` + RBAC.

## 3. Необходимые операции (и где они в дорожной карте)

| Операция | Схема | Статус | Что добавить |
|---|---|---|---|
| Жизненный цикл поиска | `searches` | есть | closeout-поля, причины завершения |

| Сектора/зоны | `search_sectors` | есть (jsonb) | PostGIS-геометрия, редактор, назначения |
| Назначения группа↔сектор↔период | `task_assignments` | есть | валидация специалистов, UI |

## 4. Карта и отрисовка зон поиска

### 4.1 ГИС-основа
- **Рекомендация:** включить расширение **PostGIS**; добавить колонку `geom geometry(Geometry,4326)` рядом с `jsonb`
  (для офлайна клиент хранит jsonb, сервер считает пространственно по `geom`).
- Альтернатива (меньше зависимостей): оставить `jsonb` и считать покрытие/буферы на клиенте — но тогда нет
  серверных проверок пересечений и нельзя строить отчёты по геометрии в БД.

### 4.2 Зоны для пеших групп
- Сектор-полигон разбивается на **полосы прочёсывания** (sweep lanes) шириной 10–30 м в зависимости от
  проходимости/видимости; расчёт времени по скорости пешком (≈3–4 км/ч) с коэффициентом проходимости местности.
- Трек группы сравнивается с полосами → процент фактического покрытия.

### 4.3 Зоны для автомобильных экипажей
- **Коридоры вдоль дорог** (линейные зоны) с радиусом обзора от оси дороги; покрытие строится по сети дорог,
  а не сплошным полигоном.
- Для БПЛА — зоны облёта (радиус/полигон) с учётом времени полёта.

### 4.4 POD (вероятность обнаружения)
- Классическая модель усилий (person-hours / coverage): `POD = 1 - exp(-k * effort)`. Поле `pod` уже есть в `search_sectors`.
- На основе POD и покрытия — сводная вероятность обнаружения по всему поиску (аналитика).

### 4.5 Карта: что реализовать (волны)
- Редактор секторов (рисование/редактирование полигонов и коридоров), треки и replay, расчёт покрытия,
  слои опасностей (`hazards`), офлайн-пакеты карт, абстракция провайдера карт. Всё это — пока `[ ]` в дорожной карте.

## 5. Отчётность для МВД (категории, требует согласования)

> Формы и обязательность определяются нормативными актами РФ (приказы/регламенты МВД по розыску,
> взаимодействие с ЕДДС, Национальным центром помощи пропавшим и пострадавшим детям и т.п.).
> **Точные шаблоны нужно утвердить с юристом/профильным специалистом** — здесь приведены только категории.

- **Инициирование:** заявление/сигнал, ориентировка (сводка-ориентировка), карточка пропавшего (без избыточных ПДн).
- **Оперативная сводка:** ход поиска, силы/средства, задействованные сектора, результаты по периодам.
- **Учёт:** журналы чек-инов, улик (с цепочкой происхождения), свидетелей, ресурсов; журнал связи/SOS.
- **Завершение:** акт о результатах поиска/закрытии, статистика, передача в архив.
- **Взаимодействие:** выгрузки/уведомления для МВД/ЕДДС в согласованном формате (XML/CSV/PDF).

Требования к реализации: экспорт (PDF/CSV/JSON), маскирование ПДн, неизменяемый audit trail, разграничение доступа,
локализация (RU). Без утверждённых шаблонов выгружать «официальные» формы недопустимо.

## 6. План по волнам (связка с `IMPLEMENTATION_ROADMAP.md`)

- **Волна A — Модель данных/основа:** PostGIS + `geom`, `specialist_qualifications`, `team_roles`,
  `search_closeout`, иммутабельный архив/replay, таблицы шаблонов отчётов.
- **Волна B — Операции + API/UI:** сектора (рисование/назначения), задачи↔группа↔сектор↔период, чекины+эскалация,
  SOS, улики/свидетели (ограниченный доступ), ресурсы, брифинг/дебрифинг, closeout.
- **Волна C — Карта/ГИС:** редактор зон, треки/replay, покрытие, POD, опасности, офлайн-карты, провайдер-абстракция.
- **Волна D — Отчётность/МВД:** экспортируемые шаблоны, маскирование ПДн, интеграция с согласованными форматами.
- **Волна E — Поле/мобильное:** регистрация устройств, синхронизация/offline, GPS-reconnect, SOS с клиента.
- **Сквозное:** юридическое/операционное согласование, security-скан, бэкап/DR, observability — до реальных данных.
