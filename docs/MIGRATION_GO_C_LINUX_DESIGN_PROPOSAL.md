# KuKLA: предложение по миграции на Go/C и Ubuntu 26.04 LTS

> **Статус:** базовое предложение утверждено владельцем проекта с условием будущей поставки Windows `.exe`. Документ обновляется для кроссплатформенной архитектуры; код и новая схема БД здесь не реализованы.
>
> **Основание:** владелец подтвердил Ubuntu, поручил самостоятельно выбрать остальные решения и подтвердил будущую адаптацию под Windows. Функциональные замены, способные изменить реальные полевые или заявительские сценарии, по-прежнему не считаются одобренными только фактом выбора платформы.

## 1. Резюме и границы предложения

Цель — получить самостоятельное desktop-приложение KuKLA для локальной работы в ВМ под Ubuntu 26.04 LTS, без обязательного Интернета, облака, внешнего сервера или root-доступа во время штатной работы. В приложение входят прикладная логика на Go, локальное хранилище, GUI и необходимые нативные компоненты C.

Предлагаемая базовая поставка:

1. Linux-поставка для Ubuntu 26.04 LTS запускается обычным пользователем; тот же Go-доменный слой собирается для последующего Windows x86_64 выпуска.
2. GTK 4 на C — общий GUI toolkit для Linux и Windows. Интерактивная карта использует общий локальный web bundle через платформенный WebView adapter: WebKitGTK на Linux и WebView2 на Windows. Ресурсы и тайлы не загружаются с CDN.
3. Встроенный Go-сервис запускается приложением, не требует ручной настройки и не открывает TCP-порты по умолчанию. IPC: Unix-сокет на Linux, именованный канал с ACL на Windows.
4. SQLite с транзакциями, миграциями и R*Tree как локальная БД. SQLCipher предлагается для шифрования БД; медиа и резервные копии также шифруются.
5. Геоданные в GeoPackage с R*Tree; импорт/экспорт GeoJSON/GPX.
6. Карта работает офлайн с локальным пакетом данных. OSM/2ГИС не обязательны; распространение карт требует проверки источника и лицензии.
7. Симулятор полевых ролей для ВМ; GPS, импорт треков, медиа и SOS проверяются без физического оборудования.
8. Сетевой API для будущих клиентов отключён по умолчанию.
9. Linux: `.deb`; Windows: отдельный установщик `.exe` с `KuKLA.exe`, Go engine и согласованными GTK/WebView runtime-компонентами. Windows требует отдельной VM-приёмки.

Базовая архитектура утверждена с условием будущей Windows-поставки. При этом удалённая работа реальных мобильных клиентов и публичный доступ заявителя не считаются эквивалентными локальному симулятору/форме: эти сценарии сохраняются отдельными требованиями и не должны молча исключаться из оценки готовности.

## 2. Фактическая база и ограничения

### 2.1. Что доступно в репозитории

В текущей ветке найдены:

- `server/src/` — Fastify/TypeScript API;
- `server/sql/001_init.sql`–`008_backfill_search_creators.sql` — SQL-миграции PostgreSQL;
- `desktop/src/` и `desktop/src-tauri/` — React-клиент в оболочке Tauri/Rust;
- `mobile/lib/` — Flutter-клиент с локальным SQLite-кэшем и очередью команд;
- `infrastructure/docker-compose.yml` и скрипты резервного копирования/восстановления;
- документы требований, архитектуры, статуса и пробелов;
- лицензия GPL-3.0-or-later.

Исходники — свидетельство о ранее реализованных сценариях, но не доказательство того, что текущая рабочая база или развёрнутая серверная среда существуют. SQL-схема не заменяет потерянные данные.

### 2.2. Известный текущий объём реализации

Рабочая основа в репозитории охватывает авторизацию и сессии, роли, поиски, участников, задачи, события, GPS, снимок операции, карту с точкой и GPS-треком, а также мобильный офлайн-кэш и очередь команд.

Часть предметных таблиц — команды, сектора, периоды, ресурсы, зацепки, свидетели, check-in, уведомления, SOS, evidence, конфликты синхронизации — создана как схема или задел. Для многих из них сквозной API и UI отсутствуют. В документации также названы незавершёнными realtime-рассылка, конфликтное разрешение синхронизации, полноценные уведомления, автономные карты и отчётность.

Текущая карта использует внешние OSM-тайлы; текущая схема не включает PostGIS. Это не удовлетворяет автономному картографическому требованию без отдельного локального источника карт.

## 3. Предварительная функциональная спецификация

Обозначения: **[ИЗВЕСТНО]** — указано во входном описании или коде; **[ЗАДЕЛ]** — есть схема или план, но не завершённый пользовательский процесс; **[ТРЕБУЕТ УТВЕРЖДЕНИЯ]** — предлагается, но влияет на поведение.

### 3.1. Роли и зоны ответственности

Из входных требований известны роли:

| Роль | Функции, подтверждённые входным описанием |
|---|---|
| Координатор | Операции, карта, задачи, ресурсы, аналитика, отчёты |
| Инфорг | Регистрация заявок, хронология, заявитель, статусы, данные и медиа |
| Старший на месте | Оперативная карта, назначение задач, чек-листы, позиции, экстренные сигналы |
| Старший поисковой группы | Маршруты/зоны, задачи группы, отчёты и связь со старшим на месте |
| Спасатель | Собственные задачи и позиция, геометки, медиа, SOS |
| Заявитель | Подача обращения и материалов, просмотр собственного статуса и доступных отчётов |

Из текущего репозитория дополнительно известны глобальные роли `SYSTEM_OWNER`, `SUPERADMIN`, `SUPERUSER`, `ADMIN`, `LEADER`, `COORDINATOR`, `SEARCHER`, `VIEWER` и роли организации `OWNER`, `ADMIN`, `COORDINATOR`, `MEMBER`, `OBSERVER`.

**Предлагаемая модель разрешений:** проверить права на уровне сервиса при каждом чтении и изменении; ограничивать данные конкретной операцией, организацией и заявкой; выдавать заявителю доступ только к принадлежащему ему обращению; критические операции аудировать. В UI скрытие кнопок не считается защитой.

**[ТРЕБУЕТ УТВЕРЖДЕНИЯ]** Таблица сопоставления восьми ролей репозитория шести ролям требований отсутствует. До утверждения точного соответствия нельзя автоматически выдавать старые роли новым пользователям или менять их возможности. Разумный проектный вариант — сохранить совместимые роли и добавить явные гранты permissions, отображая пользовательские роли в настройках; этот вариант не означает, что переименование/слияние уже одобрено.

### 3.2. Предлагаемый состав экранов

Desktop-навигация предлагает разделы:

1. Вход и смена пароля; первый запуск и создание первого администратора.
2. «Операции»: список, фильтры по статусу/району/периоду, создание и открытие карточки.
3. «Рабочее место операции»: сводка, карта, список задач, групп, ресурсов и участников.
4. «Карта»: слои, маркеры, зоны, маршруты, фильтры, легенда, карточка объекта, редактирование геометрии.
5. «Заявки»: очередь, карточка заявителя/пропавшего, хронология, медиа; включается после утверждения отличий заявки от операции.
6. «Полевой режим/симулятор»: выбор пользователя/группы, назначенные задачи, тестовая позиция, чек-лист, отчёт, тестовое медиа и SOS.
7. «События и уведомления»: журнал операции, фильтры, подтверждение уведомлений, критические сигналы.
8. «Отчёты»: предварительный просмотр, печать, PDF/CSV/XLSX экспорт.
9. «Пользователи и роли»: аккаунты, активность, ролевые права и членство в организации/операции.
10. «Данные и настройки»: карты, резервные копии, импорт/экспорт, безопасность, диагностика и локальная конфигурация.

Формы должны иметь состояния загрузки/пустого результата/ошибки/повторной попытки. Удаление медиа и значимых записей требует подтверждения и проверки прав. Опасные события не могут быть представлены только цветом: нужны текст, значок, дата/время и подтверждение.

Горячие клавиши проектируются с учётом доступности: поиск, обновление, сохранение, закрытие диалога, переключение разделов; точные комбинации фиксируются при UI-прототипировании. Контекстное меню — для карты и строк таблиц. Диалоги выбора/сохранения — GTK. Копирование/вставка, масштабирование, drag-and-drop файлов и системные уведомления — через платформенные интерфейсы, когда они доступны.

### 3.3. Процессы

Известны и должны быть трассированы к тестам:

1. Приём заявки/регистрация субъекта и создание либо связывание с операцией.
2. Первичный сбор данных, местоположение и география поиска.
3. Создание периода, брифинг, распределение людей, групп и ресурсов.
4. Разделение территории на сектора/задачи; назначение группе/исполнителю.
5. Полевая отметка начала/завершения задачи, check-in и позиция.
6. Добавление наблюдений, зацепок, свидетельств, опасностей и медиа.
7. Изменение плана и статуса при поступлении новых данных.
8. Обработка SOS/HELP/медицинского события и отметка получения/разрешения.
9. Ведение хронологии/аудита, завершение периода/поиска, разбор и архив.
10. Формирование локальных отчётов, экспорт, резервное копирование и перенос между ВМ.
11. Отложенное сохранение действий offline; последующая доставка и разбор конфликтов, если сетевой обмен включён.

Правила жизненного цикла заявки, допуска пользователя к поиску, статусов, повторного открытия и закрытия операции отсутствуют как полностью согласованная спецификация. В новом коде их нельзя домысливать.

### 3.4. Известные значения статусов

Предложение — не менять уже найденные значения до отдельной таблицы переходов:

- поиск: `PLANNED`, `ACTIVE`, `PAUSED`, `COMPLETED`, `CANCELLED`;
- задача: `OPEN`, `IN_PROGRESS`, `DONE`, `CANCELLED`;
- период: `PLANNED`, `ACTIVE`, `CLOSED`;
- сектор: `UNSEARCHED`, `ASSIGNED`, `SEARCHING`, `COMPLETE`, `SUSPENDED`;
- группа: `AVAILABLE`, `ASSIGNED`, `SEARCHING`, `RETURNING`, `OFFLINE`, `EMERGENCY`;
- зацепка: `NEW`, `CONFIRMED`, `DISMISSED`, `RESOLVED`;
- ресурс: `AVAILABLE`, `ASSIGNED`, `IN_USE`, `UNAVAILABLE`, `LOST`;
- check-in: `OK`, `DELAYED`, `HELP`, `EMERGENCY`;
- SOS: `OPEN`, `ACKNOWLEDGED`, `RESOLVED`, `CANCELLED`;
- синхронизация: `RECEIVED`, `APPLIED`, `REJECTED`, `CONFLICT`.

Для обращения заявителя, медиа и чек-листа конкретные статусы/переходы не заданы. Будут добавлены только после утверждения предметных правил.

## 4. Модель данных

### 4.1. Логическая модель

Предлагаемые агрегаты и связи:

- **Организация** — пользователи, роли организации, операции и участие организаций.
- **Пользователь/сессия** — локальная учётная запись, хеш пароля, состояние активности, гранты доступа и отзываемые сессии.
- **Заявка** — контакт заявителя, исходные сведения, вложения и история. Её отдельность от операции должна быть утверждена.
- **Поисковая операция** — статус, район, описание, точка происшествия, создатель, время начала/окончания и организации.
- **Субъект поиска** — имя, описание, одежда, важные сведения, фото/медиа, последняя известная точка/время. Чувствительные поля выдаются только уполномоченным ролям.
- **Оперативный период** — время, название, брифинг/дебрифинг.
- **Группа/участник/ресурс** — позывной, тип, руководитель, состав, доступность и назначения.
- **Сектор/маршрут/объект карты** — геометрия, тип/слой, статус, приоритет, отметки и автор изменения.
- **Задача/назначение** — исполнитель или группа, сектор, период, приоритет, состояние и временные отметки.
- **Позиция/трек** — операция, пользователь/устройство, время записи, время приёма, координаты, точность, высота, скорость и источник (`DEVICE`, `MANUAL`, `SIMULATION`, `IMPORT`).
- **Событие/аудит** — тип, операция/объект, пользователь, момент времени, источник, корреляция, безопасно отредактированное описание изменения.
- **Зацепка/свидетель/опасность/check-in/SOS/уведомление** — отдельные доменные объекты с автором, временем, состоянием и ролевым доступом.
- **Медиа** — метаданные, тип MIME, размер, SHA-256, геотеги, связь с заявкой/операцией/событием и ключ локального файла.
- **Синхронизация** — исходящая команда, идентификатор идемпотентности, устройство, попытки, ответ, конфликт и решение.
- **Карта/отчёт/настройка** — локально установленный пакет карты, результат генерации отчёта и несекретные настройки.

### 4.2. Предлагаемая физическая база

| Область | Предложение |
|---|---|
| DB | SQLite в режиме WAL, `foreign_keys=ON`, busy timeout, транзакции для доменных изменений, `STRICT`-таблицы там, где допустимо |
| ID | UUID, хранимые как TEXT в переносимой первой версии; единая генерация в сервисном слое |
| Время | UTC в целочисленных миллисекундах или согласованном ISO-8601 формате; отображение в локальном часовом поясе ВМ |
| Геометрия | GeoPackage-совместимые геометрические BLOB/метаданные; WGS84/EPSG:4326 для обмена GPS, код CRS хранится явно |
| Пространственные индексы | SQLite R*Tree по bbox; точная проверка пересечения/вхождения выполняется геометрической библиотекой, не одним bbox |
| Обмен | GeoJSON для геометрий; GPX для треков; GeoPackage для согласованного набора слоёв |
| Вложения | Вне SQLite в каталоге приложения, имена по случайному ID/хешу; в БД только метаданные и относительный storage key |
| Миграции | Нумерованные миграции, checksum, блокировка процесса и запись версии; повторный запуск миграций идемпотентен |
| История | Версия записи/optimistic locking плюс append-only аудит; текущие данные не заменяют хронологию |
| Очередь | Таблица outbox с UUID команды, типом, целевой сущностью, временем, payload, числом попыток и последним результатом |

`SpatiaLite` не предлагается обязательной зависимостью первого выпуска: она увеличит сложность поставки C-библиотек и ABI. R*Tree подходит для быстрого отбора кандидатов по прямоугольнику; точные геометрические операции должны выполняться отдельным проверенным Go-модулем. Если тесты покажут недостаточную точность/производительность, SpatiaLite или локальный PostgreSQL/PostGIS выносится в отдельное архитектурное решение, а не подключается молча.

### 4.3. Предварительный список таблиц

Ниже — логический перечень; имена и нормализация SQL-схемы уточняются после утверждения модели:

`organizations`, `users`, `role_grants`, `sessions`, `intake_requests`, `operations`, `operation_organizations`, `subjects`, `operational_periods`, `teams`, `team_members`, `resources`, `sectors`, `routes`, `map_features`, `tasks`, `task_assignments`, `positions`, `tracks`, `clues`, `witnesses`, `hazards`, `checkins`, `emergency_events`, `notifications`, `media_assets`, `operational_events`, `audit_events`, `outbox`, `sync_operations`, `sync_conflicts`, `map_packages`, `report_runs`, `app_settings`, `schema_migrations`.

В каждой изменяемой сущности предусматриваются `id`, `created_at`, `updated_at`, `created_by` (если применимо) и `version`; обязательность этих полей зависит от типа объекта. Физическое удаление критических operational/audit записей по умолчанию запрещается; архивирование и удаление персональных данных должны соответствовать утверждённым правилам хранения.

### 4.4. Ограничения, индексы и согласованность

- CHECK: диапазоны широты/долготы, точности, процентов POD, приоритетов, размера и enum-кодов.
- UNIQUE: нормализованный логин, код сектора в операции, ключ идемпотентности команды, checksum медиа.
- Индексы: операции по статусу/времени; участники по операции и пользователю; задачи по операции/статусу/группе; события по операции/времени; позиции по операции/пользователю/времени; уведомления по получателю/неподтверждённости; медиа по доменной связи; outbox по состоянию/времени.
- Все изменения состояния, аудит-запись и outbox-команда при сетевой синхронизации фиксируются в одной транзакции.
- Повтор запроса с тем же idempotency key не создаёт второй event/position/command.
- Конфликт версии не перезаписывает более свежие данные молча: обе версии сохраняются, пользователь с полномочиями получает задачу разбора.

### 4.5. Резервное копирование и перенос

1. Команда «Создать резервную копию» согласованно фиксирует DB и связанные медиа; результат — архив с manifest, версией приложения/схемы, контрольными суммами и временем.
2. Резервная копия шифруется; по умолчанию хранится вне каталога активной БД, в выбранном пользователем месте.
3. Локальные карты могут исключаться из копии как крупные переустанавливаемые пакеты, но manifest фиксирует нужные идентификаторы и версии; включение карт — настройка экспорта.
4. Восстановление сначала проверяет подпись/шифрование, manifest, контрольные суммы и `integrity_check`, затем предлагает отдельное восстановление либо явную замену активного профиля.
5. После восстановления выполняются миграции и контроль связей; ошибка не оставляет полузаменённую активную БД.
6. Перенос между ВМ выполняется экспортом/импортом такого архива на USB/локальный носитель; сетевой аккаунт или облачное хранилище не требуется.

**[ТРЕБУЕТ УТВЕРЖДЕНИЯ]** Срок хранения, RPO/RTO, включение карт в резервную копию, шифрование ключом пользователя/системным keyring и регламент удаления персональных данных.

## 5. Архитектура сервисного слоя

### 5.1. Модули Go

- `identity`: локальная аутентификация, сессии, деактивация учётных записей;
- `authorization`: роли, разрешения, область операции/организации/заявки;
- `intake`: приём обращений и связь заявка—субъект—операция;
- `operations`: жизненный цикл операций и периоды;
- `planning`: группы, ресурсы, секторы, маршруты, назначения;
- `field`: задачи, check-in, позиции и треки;
- `events`: хроника событий и аудит;
- `emergency`: SOS/HELP и подтверждение/разрешение сигналов;
- `media`: файловый каталог, безопасное копирование, хеши и метаданные;
- `maps`: провайдеры локальных пакетов, геометрии, импорт/экспорт;
- `sync`: outbox/inbox, повторные попытки, идемпотентность и конфликты;
- `notifications`: внутриприкладные уведомления и опциональные Linux-уведомления;
- `reports`: локальные представления, PDF/CSV/XLSX и печать;
- `backup`: атомарная копия, проверка и восстановление;
- `diagnostics`: журналы приложения, health state, диагностический пакет;
- `config`: XDG-пути, локальная конфигурация и отключённые по умолчанию интеграции.

Доменная логика не импортирует GTK, WebKit, HTTP или SQLite напрямую. Между ней и SQLite — интерфейсы репозиториев; сервисы транзакций владеют границами транзакций. Интеграции — через интерфейсы-порты.

### 5.2. Локальное взаимодействие и API

- Платформенный IPC без TCP: Unix domain socket в `$XDG_RUNTIME_DIR/kukla/` на Linux (каталог `0700`, сокет `0600`); именованный канал Windows с ACL текущего пользователя на Windows.
- Go-контракты и wire protocol общие; различаются только реализации `LocalTransport` с Linux/Windows build tags.
- GUI передаёт типизированные команды и события через версионированный протокол; ошибки имеют стабильный код, безопасное описание и correlation ID.
- Внутренний API не допускает анонимного доступа. Опциональный REST/WebSocket для мобильного клиента отключён по умолчанию. LAN-режим требует явного включения, TLS 1.3, регистрации/отзыва устройств и предупреждения о порте/фаерволе.
- Базовая поставка на обеих ОС не открывает TCP-порт. Wildcard-bind запрещён без отдельного подтверждения.

### 5.3. Ошибки, фоновые задания, миграции

- Ошибки валидации, отказа в доступе, конфликтов, отсутствия носителя, повреждения DB и временной ошибки синхронизации различаются по коду.
- Повторяются только временные сетевые/файловые ошибки с exponential backoff и jitter; бизнес-конфликты не повторяются автоматически.
- При остановке приложение перестаёт принимать команды, завершает текущую транзакцию и закрывает SQLite. Незавершённые outbox-записи остаются устойчивыми.
- Единственный процесс-владелец DB блокируется file lock; повторный запуск открывает уже работающий UI/показывает понятное сообщение, а не запускает конкурентный writer.
- Миграции идут до открытия основного экрана; сбой откатывает транзакцию, показывает инструкции восстановления и сохраняет диагностический лог без секретов.
- Redis, Docker, Nginx и внешний планировщик не являются зависимостями базового desktop-пакета.

## 6. Desktop и UI

### 6.1. Предлагаемый технологический выбор

**GTK 4 (C)** — общий GUI toolkit для Linux и Windows: окна, меню, таблицы, диалоги, печать, clipboard, drag-and-drop и accessibility. GTK/WebView изолируются от доменного слоя Go через C ABI и платформенные адаптеры.

Карта использует общий локально поставляемый HTML/JS bundle за интерфейсом `MapWebView`: WebKitGTK на Ubuntu и WebView2 на Windows. Используется локальная схема/ресурсы, не localhost; запрещены CDN и внешние ресурсы по умолчанию. Windows installer включает фиксированную WebView2 runtime версию для офлайн-установки либо проверяет согласованный офлайн runtime kit.

GTK 4/C и WebView — дополнительные GUI-зависимости поверх Go/C. Будущий Windows `.exe` требует отдельной Windows-сборки и проверки GTK, IPC, уведомлений, keyring и установщика; переименование Linux-бинарника в `.exe` не считается портированием.

### 6.2. Окна/разделы и сценарии

- **Первый запуск:** каталоги, создание первого администратора, мастер шифрования/ключа и выбор каталога резервных копий; без запроса root.
- **Операции:** список и фильтры; создание/редактирование; история статусов; быстрые сводные показатели.
- **Карточка операции:** данные субъекта, оперативные периоды, участники, группы, задачи, ресурсы, события и хронология.
- **Карта:** offline-first; масштабирование, перемещение, выбор слоя, поиск объекта, фильтрация, легенда, всплывающая карточка; добавление/редактирование точки/линии/полигона с подтверждением сохранения.
- **Полевая роль/симулятор:** тестовые/импортированные позиции, назначенные задачи, отметка результата, чек-лист после подтверждения формы, тестовые фото/видео, SOS с явно отмеченным режимом симуляции.
- **Инфорг/заявитель:** локальная форма и кабинет рассматриваются как desktop-модули. Они не дают удалённому заявителю доступ из Интернета и не заменяют публичный портал без отдельного сетевого компонента.
- **Отчёты:** предварительный просмотр, печать через системный диалог, экспорт в выбранный формат и сохранение копии в пользовательский каталог.

### 6.3. Масштабирование, локализация, сообщения

- DPI/HiDPI, масштаб 100–200%, клавиатурная навигация, системные шрифты, светлая/тёмная тема при поддержке GTK.
- Часовые отметки хранятся UTC, интерфейс показывает часовой пояс ВМ и явную зону при экспорте.
- Русский интерфейс — целевой язык на основании текущих экранов; остальные языки не предполагаются без подтверждения.
- В критической ошибке интерфейс показывает, что было сохранено, что ожидает отправки и где искать журнал; повторная команда не создаёт дубликат.
- Опасные действия (отмена операции, удаление файла, подтверждение/закрытие SOS, восстановление backup) требуют контекстного подтверждения и аудита.

## 7. Карта, позиции и offline

### 7.1. Карта

- Абстракция `MapProvider`: локальный GeoPackage/MBTiles, тестовая сетка/симулятор, опциональный сетевой провайдер.
- В поставке нет обязательных удалённых URL тайлов, API-ключа 2ГИС или CDN.
- Реальные локальные карты устанавливаются импортом проверенного пользователем пакета, поставленного на носителе либо включённого в согласованную сборку с лицензией.
- При отсутствии карт приложение показывает пустую/тестовую координатную сетку и данные-объекты; оно не делает вид, что предоставляет реальную подложку.
- 2ГИС — только отдельный опциональный адаптер при наличии договора/ключа и согласии на сеть. OSM-данные и тайлы не скачиваются методом массового scraping публичного tile-сервера.
- Геометрии: точки, линии, полигоны; проверка валидности, вершины, bounding box, импорт/экспорт, undo/redo и аудит каждой сохранённой версии.
- Ручное построение зон/маршрутов обязательно в объёме входных требований. Алгоритм автопостроения маршрута не задан; он не вводится без спецификации препятствий, рельефа, допустимых путей и правил безопасности.

### 7.2. Позиционирование

- Источники: устройство (если появится), ручной ввод, импорт GPX и детерминированный симулятор.
- Сохраняются `recorded_at`, `received_at`, источник, точность, высота, скорость и автор/устройство.
- Точная частота — настройка, но исходные значения 30 секунд в движении и 5 минут в покое — только кандидат до подтверждения.
- В ВМ без GPS нельзя показывать «реальную позицию»; экран маркирует симуляцию, импорт или ручной ввод.
- Симулятор может воспроизвести маршрут с ускорением/паузой и генерировать тестовые события, но не используется для реального мониторинга.

### 7.3. Offline-синхронизация

- Локальное действие фиксируется в DB и outbox одной транзакцией.
- Каждая команда имеет UUID/idempotency key, локальное время, автора, версию сущности и payload.
- При недоступности сети событие не теряется; UI показывает очередь и последнюю попытку.
- После восстановления связи применяется retry с backoff; явный acknowledgement удаляет/закрывает outbox-команду.
- Для конфликтующей версии серверная запись не затирает локальную. Сохраняются обе версии, решение принимается уполномоченным пользователем и аудируется.
- Правило «последняя запись побеждает» не используется для SOS, статусов операции, назначений, свидетельств, геометрий и доказательств.
- В полностью локальном режиме синхронизация отключена, но данные и журнал работают.

**Ограничение:** доставка удалённого сигнала/SOS, realtime-позиции телефона и портал вне ВМ физически невозможны без сети. При обрыве сети приложение сохраняет событие локально, визуально помечает его как недоставленное и не сообщает ложное подтверждение получателю.

## 8. Медиа, отчёты, уведомления

### 8.1. Медиа

- Локальный каталог по случайным идентификаторам, без использования имени файла как пути.
- Проверка расширения, сигнатуры файла/MIME, размера и прав; лимиты настраиваемые.
- Запись через временный файл, fsync/rename и checksum для защиты от частичной записи.
- Привязка к заявке/операции/событию; геотеги и время съёмки сохраняются как метаданные, если доступны.
- Предпросмотр ограничивает чтение недоверенных форматов; оригинал остаётся неизменным.
- Удаление только с правом, подтверждением, аудиторской записью и согласованной политикой retention.
- Физические фото/видео в демо-режиме помечаются как тестовые.

### 8.2. Отчёты/печать

Предусмотреть локальные отчётные представления для операций, заявок, групп, задач, ресурсов, временной шкалы, позиций/треков и событий. Экспорт — PDF, CSV и XLSX, если соответствующий формат подтверждён; печать — через стандартный диалог системы, а PDF остаётся доступен при отсутствии принтера.

Поля, формулы, шапки, подписи, логотипы, нумерация и юридическая значимость печатных форм неизвестны без образцов. Они не должны быть придуманы в качестве «точной копии». До получения эталонов отчёты считаются черновыми техническими выгрузками.

### 8.3. Уведомления

- Внутренний центр уведомлений и история в БД — обязательная базовая доставка.
- Критические события выделяются в панели операции и сохраняются в журнале.
- Linux desktop notification через DBus используется опционально; при отсутствии службы остаётся внутриприкладное сообщение.
- Звук выключен по умолчанию, включается пользователем; фильтр и приоритеты должны быть доступны.
- Статус «показано ОС», «увидено в приложении» и «подтверждено адресатом» — разные состояния; отправка уведомления ОС не считается подтверждением получения SOS.

## 9. Безопасность и эксплуатация

### 9.1. Локальные учётные данные

- Пароль хранится только в хеше Argon2id с параметрами, проверяемыми на целевой ВМ.
- Роли проверяются Go-сервисом при каждом доступе к объекту.
- Сессии имеют срок действия, отзыв и аудит входа/выхода; регистрация новых пользователей по умолчанию закрыта.
- Приложение не содержит demo-паролей или production-секретов.
- WebView использует локальный content security policy, запрещает remote script/frame/resource по умолчанию и не открывает произвольные локальные файлы.

### 9.2. Шифрование/права

**Предлагаемый безопасный default:** SQLite на SQLCipher; медиа и backup шифруются отдельным ключом через проверенный криптографический механизм. Ключ хранится в Linux Secret Service/libsecret или Windows Credential Manager/DPAPI. Если системное хранилище недоступно, приложение запрашивает master passphrase и не создаёт незашифрованный экземпляр молча.

- Linux XDG-каталоги данных/состояния — только владельцу (`0700` каталоги, `0600` чувствительные файлы); Windows использует NTFS ACL для текущего пользователя.
- Секреты не пишутся в журналы, экспорт и диагностический пакет.
- Резервные копии шифруются независимо от исходной DB; восстановление проверяет целостность.
- Администратор ОС/root может прочитать или подменить файлы приложения; hash-chain аудита помогает обнаружить изменение, но не обещает защиту от root. В документации это ограничение явно указывается.

### 9.3. Каталоги XDG

Linux XDG: конфигурация `~/.config/kukla/`; данные/DB/медиа `~/.local/share/kukla/`; кэш `~/.cache/kukla/`; журналы/состояние `~/.local/state/kukla/`; runtime socket `$XDG_RUNTIME_DIR/kukla/`.

Windows: конфигурация `%APPDATA%\\KuKLA\\`; DB и медиа `%LOCALAPPDATA%\\KuKLA\\Data\\`; кэш `%LOCALAPPDATA%\\KuKLA\\Cache\\`; журналы `%LOCALAPPDATA%\\KuKLA\\Logs\\`; именованный канал создаётся с ACL текущего пользователя. Windows использует NTFS ACL вместо POSIX mode bits.

На обеих платформах backup хранится в выбранном пользователем каталоге/на носителе, не рядом с единственной активной DB. Пакеты офлайн-карт могут храниться отдельно; backup фиксирует их версию и включает их по выбору пользователя.

### 9.4. Логи и диагностика

Раздельно ведутся app/error, user audit, background job, sync, integration и emergency журналы. Предлагается структурированный формат с ротацией, ограниченным сроком/объёмом и удалением секретов/лишних персональных данных. Диагностический архив формируется локально и перед сохранением показывает список включаемых файлов. Критические журналы не отправляются в облако.

### 9.5. Запуск/остановка/восстановление

- Linux: запуск из меню/CLI `kukla`; Windows: `KuKLA.exe`. Штатная работа — от обычного пользователя.
- Первый запуск создаёт соответствующие OS-каталоги, зашифрованную пустую DB и администратора; demo-данные добавляются только по явному выбору.
- GUI запускает Go engine как дочерний процесс и корректно останавливает его после завершения текущей транзакции.
- Повторный запуск на Linux обнаруживает экземпляр через runtime socket; Windows использует named pipe/instance mutex.
- При падении engine GUI показывает offline/read-only состояние, ограничивает безопасные попытки восстановления и проверяет идемпотентность перед повтором команды.
- Автозапуск на Linux — опциональный `systemd --user`; Windows — per-user Startup/Task Scheduler по явному согласию. Системная служба/root не нужны для базового запуска.

| Формат | Роль | Плюсы | Минусы/ограничения |
|---|---|---|---|
| `.deb` | Основной пакет для Ubuntu 26.04 LTS | Интеграция с меню/desktop-файлом, явные зависимости, удаление пакетным менеджером | Для установки могут понадобиться root и локальные пакеты-зависимости; runtime не должен требовать сети |
| AppImage | Дополнительный переносимый вариант после тестов | Удобно переносить/запускать без установки | GTK/WebKit/DBus интеграция и размер; не гарантирует полностью bundled host stack |
| `tar.gz` | Диагностика/эксперты/изолированная установка | Простая переносимость и проверка checksum | Пользователь сам управляет интеграцией, зависимостями и обновлением |
| Flatpak | Не основной для первой автономной поставки | Изоляция и системный install/update flow | Репозитории/runtime требуют отдельной подготовки для offline-обновлений |
| Windows installer `.exe` | Следующий обязательный платформенный этап | Упаковывает приложение, engine и runtime для офлайн-установки | Размер, подпись/SmartScreen, WebView2 runtime и отдельные Windows VM-тесты |

Предлагается выпускать подписанный `.deb` и manifest/checksum; офлайн-кит включает пакет и согласованные зависимости. Для Windows последующим артефактом будет `KuKLA-Setup.exe`, устанавливающий `KuKLA.exe`, Go engine, GTK runtime и фиксированный WebView2 runtime либо проверяющий локальный офлайн runtime kit. Удаление приложения на обеих ОС не удаляет пользовательскую БД/медиа без отдельного подтверждения. Обновление выполняется после backup и проверки миграции/rollback.

## 11. План реализации по этапам

Базовое архитектурное предложение утверждено владельцем. Реализация может идти поэтапно; детали, которых нет в исходных материалах (role mapping, статусы заявки, печатные формы, автопостроение маршрута и фактическая доставка SOS), остаются отдельными блокерами соответствующих функций и не выдумываются.

| Этап | Результат | Критерий готовности |
|---|---|---|
| 0. Уточнение/приёмка | Зафиксированы роли, статусы, формы, отчёты, OS/VM, сетевой режим, offline-карты | Владелец подписал трассируемую спецификацию и границы MVP |
| 1. Основа приложения | Go engine, C/GTK shell, IPC, конфигурация XDG, чистый запуск без сети | Чистая ВМ; обычный пользователь; ноль TCP-портов; повторный запуск корректен |
| 2. Хранение/безопасность | SQLite/SQLCipher, миграции, авторизация/RBAC, аудит, backup/restore | Интеграционные тесты целостности, отзыва сессий, резервного восстановления и прав |
| 3. Операционный workflow | Операции, субъекты, участники, группы, задачи, периоды и ручная хронология | End-to-end сценарии всех утверждённых ролей и статусов |
| 4. GIS и offline-карты | Импорт пакета карты, объекты/геометрии, редактирование, фильтры и экспорт | Полный сценарий карты без Интернета и проверка round-trip геометрии |
| 5. Полевой режим | Позиции, ручной ввод, GPX, симулятор, check-in, тестовый SOS/медиа | Офлайн-очередь, идемпотентность и явная маркировка симуляции |
| 6. Заявки/медиа/уведомления | Утверждённый intake, вложения, таймлайн, локальные уведомления | Ограничения доступа, integrity медиа, ошибки при недоступной службе уведомлений |
| 7. Отчёты и обмен | Утверждённые PDF/CSV/XLSX/печатные формы, import/export, опциональная синхронизация | Сверка по эталонным формам и тест конфликта/offline→online |
| 8. Linux-поставка и испытания | `.deb`, uninstall/upgrade, документация, чистые Ubuntu VM-инсталляции | Приёмка после перезагрузки, offline, restore, обновления и безопасности |
| 9. Windows follow-on | GTK C UI, Go engine, Named Pipe IPC, WebView2, Windows Credential Manager/DPAPI, `KuKLA-Setup.exe` | Установка/запуск без Интернета под обычным пользователем на чистой Windows VM; тест backup/restore и parity основных workflow |

**MVP не означает удаление функций.** Для безопасной поставки первой версии функции вводятся постепенно, но матрица трассировки сохраняет каждое требование и показывает, что ещё не готово. Реальный SOS/realtime с внешним адресатом нельзя принимать только по симулятору.

## 12. План тестирования и приёмки

### 12.1. Функциональные/ролевые тесты

- каждый пользователь входит/выходит, блокировка/деактивация немедленно прекращает доступ;
- для каждой роли выполняется таблица разрешено/запрещено по операции, заявке, медиа, геоданным, управлению пользователями и SOS;
- проверяются каждое разрешённое и запрещённое ребро графа переходов статусов; invalid transition оставляет запись без изменений;
- операция, участники, группа, ресурс, сектор, задача и назначение сохраняют ссылки и аудит;
- заявитель видит только собственные данные, если этот сценарий утверждён;
- два пользователя с похожими UUID не получают доступ друг к другу через подмену идентификатора.

### 12.2. GIS и позиции

- импорт/экспорт точки, линии, полигона, GeoJSON, GPX и GeoPackage;
- пустая карта/пакет повреждён/CRS неизвестна/геометрия самопересекается;
- фильтрация объекта, редактирование, undo/redo, сохранение, восстановление после аварии;
- число объектов и позиций растёт до заданного лимита; правильные RTree-кандидаты подтверждаются точной геометрией;
- position source сохраняется для device/manual/import/simulation; в симуляции нет ложного статуса реального GPS;
- карта, фильтры, операции и данные доступны при отключённой сети.

### 12.3. Offline/sync/SOS/media

- запись команд без сети, перезапуск, повторная отправка и подтверждение без дублей;
- конфликт одной сущности с двумя версиями, ручное решение и аудит;
- SOS при offline явно отображается как локально записанный/недоставленный, а после подключения — с delivery/ack раздельно;
- медиа неподдерживаемого типа, превышение лимита, обрыв записи, checksum-несовпадение, предпросмотр и удаление с подтверждением;
- уведомления в UI продолжают работать без службы системных уведомлений.

### 12.4. Отчёты, install, security, отказоустойчивость

- сверка каждого экспорта с эталонной таблицей/печатной формой; пустые значения, timezone и длинные строки;
- установка на чистую ВМ, offline-установка из kit, запуск после reboot, uninstall с сохранением/удалением данных по выбору;
- upgrade со старой копии, ошибка миграции, восстановление из backup и перенос на другую ВМ;
- повреждённая конфигурация/DB, отсутствующая папка, диск почти заполнен, read-only файл, медленный диск, ограниченная RAM;
- длинные списки, большие объёмы GPS/геометрий и медиа; числа предельных объёмов фиксируются после VM sizing;
- проверка ввода, SQL injection, path traversal, небезопасных URL/WebView, лишних прав файлов, утечки секретов в логах, подделки локальных сообщений и отзыва сессии;
- Linux: Wayland/X11 при наличии, HiDPI, отсутствующий принтер, clipboard, DBus notifications отключены; Windows: чистая VM, NTFS ACL, Credential Manager/DPAPI, WebView2 fixed/offline runtime, Start Menu, uninstall/update;
- GTK/C/Go сборка проверяется на Windows runner и запускается в Windows VM; Wine-only проверка не является приёмкой;
- отдельная функциональная и security-приёмка с пользователями полевого поиска до применения в реальных экстренных операциях.

## 14. Риски и меры

| Риск | Последствие | Мера |
|---|---|---|
| Нет эталонных форм/исторических сценариев | Нельзя доказать сохранение пользовательского поведения | Получить примеры до приёмки отчётности и workflow |
| Удалённый портал/mobile несовместимы с полностью локальным режимом | Потеря внешнего доступа/полевой доставки | Отдельно утвердить optional LAN/API/mobile либо согласовать desktop-mode как замену |
| ВМ offline без пакета карты | Географический фон отсутствует | Поставлять/импортировать лицензированный локальный пакет, иметь ясный тестовый режим |
| SQLite пишется конкурентно из нескольких устройств | Задержки/блокировки | Один service owner для локальной БД, измерение нагрузки, Postgres только при подтверждённой необходимости |
| SOS при разрыве связи | Получатель не узнаёт о сигнале в реальном времени | Не обещать доставку без канала; отображать недоставленное состояние и приёмку на реальном канале отдельно |
| C/GTK/WebKit интеграция повышает сложность сборки | ABI/обновления платформы | Чистая Ubuntu CI/VM, pinned dependencies, минимальный bridge, smoke tests |
| SQLCipher/ключ недоступен после сбоя | Данные не открываются | Recovery key/регламент backup, key rotation tests и проверенная процедура восстановления |
| Неподтверждённое сопоставление ролей | Слишком широкий/узкий доступ | Не назначать преобразования автоматически; таблицу permissions утвердить до миграции пользователей |
| Геометрический алгоритм/маршрут не определён | Небезопасный или неверный маршрут | Ручное редактирование; автопланирование только после отдельной GIS-спецификации |
| Невозможность измерить нагрузку без VM limits | Неизвестная задержка на больших данных | Зафиксировать VM profile и целевые объёмы, выполнить нагрузочные тесты до выпуска |

## 15. Утверждение и границы

Владелец проекта подтвердил Ubuntu и утвердил предложение с условием будущей поставки Windows `.exe`. Поэтому Windows поддержка является архитектурным требованием с первого модуля, а не поздней перекладкой Linux-бинарника.

Утверждённая базовая платформа/технологический выбор:

1. Ubuntu 26.04 LTS x86_64 — первый выпуск; Windows x86_64 — последующий installer `.exe` и запускаемый `KuKLA.exe`.
2. GTK 4/C GUI как общий toolkit; WebView adapter: WebKitGTK на Linux, WebView2 на Windows; карта использует локальные ресурсы.
3. Общий Go engine, платформенный IPC: Unix socket на Linux и Named Pipe на Windows; по умолчанию TCP-порты не слушаются.
4. SQLite/SQLCipher, R*Tree и GeoPackage; локальные пакеты карт; офлайн-работа без обязательного 2ГИС/Интернета.
5. XDG/Secret Service на Linux; AppData, NTFS ACL, Credential Manager/DPAPI на Windows.
6. `.deb` как основной Linux-пакет; `KuKLA-Setup.exe` как Windows follow-on, включая зависимости для автономной установки.
7. Общий слой данных/бизнес-логики должен оставаться переносимым; Win32/WebView/криптографические и системные вызовы изолируются в platform adapters.
8. Неизвестные бизнес-статусы, ролевые сопоставления, отчётные шаблоны и алгоритм автопостроения маршрутов не выдумываются. Симулятор не считается эквивалентом удалённой доставки SOS, реального мобильного клиента или публичного портала.
9. Лицензия проекта сохраняется GPL-3.0-or-later, пока владелец не изменит требование.

Утверждение архитектуры разрешает начать поэтапную реализацию в рамках этих границ. Linux-сборка не будет объявлена Windows-совместимой, пока не пройдут Windows native build, чистая VM установка, offline тесты и проверка целостности/восстановления.
