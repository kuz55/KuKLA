# Принадлежность данных: матрица «серверное — локальное»

> Документ основан на решении [ADR-0001](adr/0001-data-ownership-server-vs-local.md).
> Он отвечает на один вопрос: **для каждой сущности — где она живёт, кто ею владеет и что происходит локально.**

## Обозначения

| Признак | Значение |
|---|---|
| **Серверное** | Источник истины — PostgreSQL. Локально может кэшироваться только для чтения или как очередь на запись |
| **Локальное** | Принадлежит устройству, на сервер не отправляется |
| **Оба** | Хранится на сервере и локально, с определённым правилом разрешения расхождений |

Дополнительный столбец «Очередь» означает: позволяет ли клиент записывать изменение без сети для последующей отправки.

---

## 1. Идентичность и доступ

| Сущность | Владелец | Локально | Очередь | Примечание |
|---|---|---|---|---|
| `users` | Серверное | Кэш только для чтения | Нет | Учётные записи создаёт сервер; публичная регистрация закрыта |
| `sessions` | Серверное | Хранится токен сессии | Нет | Токен — не данные, а ключ доступа; хранится в системном хранилище секретов |
| `system_bootstrap` | Серверное | — | Нет | Однократное создание владельца, см. `SECURITY_BOOTSTRAP.md` |
| `organizations` | Серверное | Кэш только для чтения | Нет | Справочник |
| `organization_members` | Серверное | Кэш только для чтения | Нет | Влияет на права; локально не изменяется |
| `role_grants` (план) | Серверное | Кэш только для чтения | Нет | Назначение ролей — только на сервере |
| **Техническая идентичность установки** | **Локальное** | Только локально | Нет | Без роли и без прав. Заменяет текущую запись `local-installation` |
| **Анкета (черновик до подтверждения)** | **Оба** | Да | Да | Локально — черновик; после подтверждения истина на сервере |
| **Настройки приложения** | **Локальное** | Только локально | Нет | Тема, язык, пути, параметры карты |

**Важно:** локальная запись установки обозначает *устройство*, а не *пользователя*. Роль у неё отсутствует.

> **Расхождение, которое нужно устранить в коде.** Текущая локальная миграция `rebuild/internal/storage/sqlite/migrations/005_users_and_profiles.sql` создаёт запись установки с ролью `SEARCHER`. По этому решению роль у неё должна отсутствовать, а запись должна обозначать только техническую идентичность устройства. Это правка кода, и она сознательно **не** делается в этом изменении, состоящем только из документации.

| `emergency_events` (SOS) | Серверное | Кэш + очередь на запись | Да | При отсутствии связи явно помечается как недоставленное, см. `OFFLINE.md` |

| `clues` | Серверное | Кэш + очередь на запись | Да | — |

| `sync_conflicts` | Серверное | Кэш только для чтения | Нет | Разрешение конфликтов — на сервере |

## 6. Правила обмена

1. **Локальная запись никогда не перезаписывает серверную молча.** При расхождении сохраняются обе версии, решение принимает уполномоченный пользователь.
2. **Идемпотентность.** Каждая команда имеет UUID и ключ идемпотентности. Повторная отправка не создаёт дубликат.
3. **Порядок.** Команда, действие и запись в аудит фиксируются одной транзакцией.
4. **Статусы синхронизации:** `RECEIVED`, `APPLIED`, `REJECTED`, `CONFLICT`.
5. **Отсутствие связи.** Команда сохраняется локально, отображается как недоставленная, и получатель не получает ложного подтверждения.
6. **Права — всегда на сервере.** Клиент может скрывать недоступное, но никогда не решает, разрешено ли действие.

---

## 7. Что не переносится локально

Следующие механизмы относятся к серверу и не имеют смысла в локальном режиме:

- разграничение доступа между пользователями (в локальной БД один пользователь ОС);
- изоляция данных организаций;
- ограничение частоты запросов;
- публикация портов и CORS — базовый локальный IPC использует Unix-сокет или именованный канал и не открывает TCP;
- WebSocket-рассылка: для realtime нужен второй участник канала, то есть сервер.
