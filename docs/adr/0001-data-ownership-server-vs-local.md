# ADR-0001. Источник истины и границы «серверное — локальное»

- **Статус:** принято
- **Дата:** 2026-10-07
- **Решение принято:** владельцем проекта
- **Влияет на:** `server/` (Fastify/TypeScript, PostgreSQL), `rebuild/` (Go/C desktop), `mobile/` (Flutter)

## Контекст

В проекте исторически сложились две реализации одних и тех же данных:

- `server/` — Fastify API и PostgreSQL, где уже работает авторизация, RBAC, поиски, участники, задачи, события и GPS;
- `rebuild/` — параллельный desktop-клиент на Go/C с **собственной SQLite**, созданный в рамках миграции на новый стек.

`docs/ARCHITECTURE.md` объявляет модель «server-first», где PostgreSQL хранит авторитетное состояние. При этом локальная схема `rebuild/internal/storage/sqlite/migrations/005_users_and_profiles.sql` создаёт таблицу `app_users` и записывает в неё техническую запись `local-installation` **с ролью `SEARCHER`**:

```sql
INSERT INTO app_users(id, role, active, created_at)
VALUES ('local-installation', 'SEARCHER', 1, strftime('%Y-%m-%dT%H:%M:%fZ', 'now'));
```

Так возникли **два источника истины для ролей и пользователей**. Это уже создаёт риск: локальный пользователь с ролью в клиенте выглядит так, будто он обладает правами, хотя клиент не является границей авторизации.

Кроме того, `docs/REQUIREMENTS.md` не содержит упоминаний входа по телефону, а `MIGRATION_GO_C_LINUX_DESIGN_PROPOSAL.md` требует не додумывать функциональные решения самостоятельно. Поэтому источник истины, модель авторизации и состав клиентов должны быть зафиксированы явно.

## Решение

### 1. Источник истины — сервер

**Сервер (PostgreSQL) является единственным источником истины** для всех данных, перечисленных в разделе «Серверное» документа [`DATA_OWNERSHIP.md`](../DATA_OWNERSHIP.md).

Локальная SQLite в Go/C-клиенте — это **производное хранилище**: кэш прочитанных данных плюс очередь неотправленных команд. Локальные данные никогда не переопределяют серверные и не заменяют их.

### 2. Локальное хранилище не хранит роли и пользователей

Локальная база **не хранит роли**. Признаются только:

- техническая идентичность установки (устройство/сессия), без роли и без прав;
- данные анкеты, пока она не подтверждена сервером, — как черновик, отправляемый на сервер;
- кэш серверных ответов, включая отображаемую роль, полученную от сервера.

Роль, хранимая локально, **никогда не рассматривается как разрешение**. Любая проверка прав выполняется на сервере. Сокрытие элементов интерфейса не является защитой.

Текущая запись `local-installation` с ролью `SEARCHER` подлежит приведению в соответствие с этим решением: роль у неё должна быть удалена, а сама запись должна обозначать только техническую идентичность установки.

### 3. Модель авторизации — глобальная роль плюс членство

Основанием для прав служат:

1. **глобальная роль** пользователя (`SYSTEM_OWNER`, `SUPERADMIN`, `SUPERUSER`, `ADMIN`, `LEADER`, `COORDINATOR`, `SEARCHER`, `VIEWER`);
2. **членство** в поисковой операции (`search_members`) или в организации (`organization_members`), с учётом участия организации в операции (`search_organizations`).

Это соответствует уже работающей серверной логике (`canAccessSearch`, `requireSearchAccess`, `requireSearchManagement` в `server/src/http.ts`). Роли определяют объём допустимых действий, членство определяет, к каким операциям эти действия применимы.

### 4. Состав клиентов

| Клиент | Статус | Роль |
|---|---|---|
| `rebuild/` — Go/C + GTK4 | **целевой** | Основной рабочий клиент для Linux и Windows |
| `mobile/` — Flutter | **сохраняется** | Полевой клиент; остаётся в целевой архитектуре |
| `desktop/` — Tauri + React | **deprecated** | Служит эталоном поведения до достижения паритета, затем выводится из эксплуатации |

Desktop-приложение не заменяет мобильный полевой клиент: сценарии полевой работы выполняются на телефоне.

### 5. Типы, идентификаторы и обмен

| Аспект | Сервер (PostgreSQL) | Локально (SQLite) | Правило обмена |
|---|---|---|---|
| Идентификатор | `uuid` (`gen_random_uuid()`) | `TEXT` | UUID передаётся строкой в каноническом формате |
| Время | `timestamptz` | `TEXT` | UTC, ISO-8601; локальное время — только для отображения |
| Структурированные поля | `jsonb` | `TEXT` + `CHECK (json_valid(...))` | JSON передаётся как есть; БД валидирует синтаксис |
| Перечисления | `CHECK` по списку | `CHECK` по списку | Списки значений должны совпадать; определяется в одном месте |
| Геометрия | `jsonb` / числовые поля | `TEXT` / `REAL` | Геометрия передаётся как GeoJSON |
| Числа с фиксированной точностью | `numeric(5,2)` | `REAL` | Допустимое расхождение должно быть явно определено при реализации |

Правило прямого переноса типов не работает: `uuid`, `jsonb`, `timestamptz`, `gen_random_uuid()` и частичные уникальные индексы в SQLite отсутствуют. Поэтому контракт задаётся **форматом обмена**, а не схемой SQL.

### 6. Вход по телефону

Вход по номеру телефона и одноразовому коду (OTP) вводится как требование и фиксируется в `docs/REQUIREMENTS.md`.

- Номера хранятся и нормализуются в формате E.164.
- Существующая аутентификация по email и паролю **сохраняется**: часть отрядов может работать без SMS.
- Публичная самостоятельная регистрация **закрыта**. Учётные записи создаются по приглашению или администратором.
- OTP-коды: однократные, с ограниченным сроком жизни, с ограничением частоты запросов, с аудитом событий.
- Секреты провайдера передаются только через переменные окружения и никогда не хранятся в репозитории, логах или клиенте.

### 7. Медицинские данные

Медицинские заметки (поле `subjects.medical_notes`) **не включаются** до введения шифрования данных при хранении (SQLCipher для локальной БД, шифрование резервных копий). Соответствующие поля существуют в схеме, но не используются в API и интерфейсе до выполнения этого условия.

### 8. Доступ к трекам

Трек участника — оперативные данные внутри поисковой операции. Доступ к трекам определяется членством в операции и её ролью, а не персональным ограничением по автору точки.

Правило: **любой пользователь, имеющий доступ к поисковой операции, может видеть треки её участников.** Дополнительного ограничения «только свой трек» не вводится.

## Последствия

### Положительные

- Устранено противоречие двух источников истины для ролей.
- Клиент не сможет самовольно выдать пользователю повышенные права.
- Правило доступа к трекам зафиксировано и не требует домысливания при реализации.
- Требование входа по телефону внесено в требования, а не выведено из кода.

### Отрицательные и ограничения

- Клиент без сети не может показать данные, которые он ранее не получил: полноценный офлайн ограничен кэшем и очередью.
- Требуется слой маппинга типов PostgreSQL ↔ SQLite, который нужно поддерживать синхронно.
- Локальная миграция `005_users_and_profiles.sql` требует доработки, чтобы убрать роль у технической записи установки.

### Что становится невозможным

- Объявление локальной SQLite источником истины.
- Использование локальной роли как разрешения.
- Замена мобильного полевого клиента desktop-приложением.
- Прямой перенос серверной схемы в SQLite без слоя маппинга.
