# ADR-0002. Tauri + React как кроссплатформенный desktop-клиент

- **Статус:** принято
- **Дата:** 2026-11-04
- **Решение:** выбрать Tauri + React (`desktop/`) целевым native desktop-клиентом
- **Начальные платформы:** Windows и Linux; macOS — следующим этапом
- **Заменяет:** раздел 4 ADR-0001 о составе desktop-клиентов; остальные решения ADR-0001 остаются в силе

## Контекст

В репозитории есть серверное приложение (`server/`, Fastify + PostgreSQL), React/Tauri-клиент (`desktop/`) и отдельный прототип Go/C + GTK4 (`rebuild/`). Сервер остаётся авторитетным источником общих операционных данных. Прототип `rebuild/` хранит локальные данные в SQLite и пока не подключён к серверу. Tauri-клиент уже содержит API-интеграцию, интерфейс командного центра и менеджерский search-scoped срез профилей субъектов.

Нужно зафиксировать продуктовый desktop-клиент и не смешивать нативную поставку с браузерным dev-сервером Vite. Решение по клиенту не меняет источник истины, серверную модель авторизации или назначение мобильного полевого клиента.

## Решение

1. **Целевой desktop-клиент — Tauri + React** из `desktop/`. React/Vite отвечает за интерфейс, Tauri упаковывает его в нативное приложение.
2. **Первая нативная матрица — Windows и Linux.** CI настраивается собирать Windows MSI и Linux DEB. Сборка macOS отложена на отдельный этап; она не считается проверенной.
3. **`rebuild/` остаётся локальным экспериментальным прототипом.** Go/C + GTK4 не является целевым desktop-клиентом и не должен описываться как серверный или синхронизируемый продуктовый клиент.
4. **Сервер и PostgreSQL остаются авторитетными.** Tauri обращается к серверу через API. В режиме браузерной разработки Vite использует относительный `/api/v1` и same-origin proxy; браузерный dev-сервер не является целевой поставкой.
5. **Офлайн-режим не подразумевается.** Tauri сейчас не предоставляет долговременный локальный кэш или очередь команд. Поддержка деградации сети и офлайн-сценариев требует отдельного решения, реализации и проверки.
6. **Мобильный клиент остаётся отдельным полевым клиентом.** Выбор Tauri не переносит полевые функции в desktop.

Для subject-profile slice сохраняются отдельные границы: только менеджерские роли с доступом к операции, только list/create/update; без field/mobile-доступа, загрузки фото, hard delete и offline/degraded-network поведения. Решение о клиенте не снимает незакрытые privacy/retention, audit verification, тестовые и end-to-end workflow gates. Roadmap-элемент остаётся **PARTIAL** до их закрытия.

## Рассмотренные альтернативы

- **Go/C + GTK4 как целевой клиент.** Не выбрано: текущая реализация — локальный прототип, не подключённый к серверному API; превращение его в продуктовый клиент потребовало бы отдельной миграции и повторной реализации уже имеющихся серверных интеграций.
- **Только браузерный клиент.** Не выбрано: продуктовой поставкой запрошено нативное desktop-приложение; Vite web mode остаётся средством разработки.
- **Сохранить оба desktop-стека как равноправные цели.** Не выбрано: это дублирует продуктовую работу и размывает критерии тестирования и поставки.

## Последствия и оставшаяся работа

- Документация и CI должны называть Tauri целевым desktop-клиентом, а `rebuild/` — локальным прототипом.
- Нативные Windows/Linux bundle jobs проверяют создание MSI/DEB; до успешного запуска этих jobs на CI они являются настроенными проверками, а не подтверждённым release pipeline.
- Нативная macOS-сборка пока не настроена.
- Tauri хранит session token в WebView `localStorage`; перенос в OS credential store остаётся требованием безопасности.
- Privacy/retention, production storage и backup protections, аудит и тесты subject-profile workflow, а также явное и проверенное degraded-network решение остаются блокирующими gates для завершения Subject roadmap item.
- Не считать эту архитектуру сертифицированной, production-ready или пригодной как единственную систему координации реальной спасательной операции.
