# KuKLA — План миграций базы данных v1.0

> Рабочий документ для развития PostgreSQL KuKLA. Описывает порядок перехода от текущей схемы к целевой архитектуре без потери данных и без изменения уже применённых миграций.

## 1. Цель

KuKLA должна иметь управляемую, воспроизводимую и проверяемую систему изменения структуры PostgreSQL.

Миграционный процесс обязан позволять:

* создать БД с нуля;
* обновить уже существующую БД;
* точно определить версию схемы;
* обнаруживать изменение уже применённой миграции;
* безопасно переносить существующие данные;
* проверять результат миграции;
* выполнять восстановление после ошибки.

---

# 2. Текущее состояние

Сейчас SQL-файлы KuKLA находятся в:

```text
server/sql/
```

и подключаются Docker Compose через:

```text
/docker-entrypoint-initdb.d/
```

Текущая последовательность:

```text
001_init.sql
002_seed.sql
003_operational_domain.sql
004_organizations_resilience.sql
005_rbac_bootstrap.sql
```

Такой механизм корректен для первичной инициализации нового PostgreSQL volume.

Но он **не является полноценной системой миграций существующей БД**.

Если PostgreSQL volume уже существует, появление нового SQL-файла в `docker-entrypoint-initdb.d` само по себе не гарантирует выполнение этого файла.

---

# 3. Главный принцип

Исторические миграции считаются неизменяемыми после применения.

Нельзя:

```text
изменить 003_operational_domain.sql
```

после того, как эта миграция была выполнена в среде.

Вместо этого создаётся новая миграция:

```text
006_...
```

Принцип:

```text
001
 ↓
002
 ↓
003
 ↓
004
 ↓
005
 ↓
006
 ↓
007
 ↓
...
```

---

# 4. Таблица истории миграций

Необходимо ввести отдельную таблицу:

```text
schema_migrations
```

Рекомендуемые поля:

```text
version
name
checksum
applied_at
execution_ms
```

Назначение:

* определить применённые миграции;
* не выполнять одну миграцию дважды;
* контролировать целостность файлов;
* видеть историю изменения схемы.

Пример:

```text
version | name                    | checksum | applied_at
--------+-------------------------+----------+-------------------
001     | init                    | ...      | ...
002     | seed                    | ...      | ...
003     | operational_domain      | ...      | ...
```

---

# 5. Checksum

Для каждой применённой миграции сохраняется checksum файла.

При запуске migration runner:

```text
файл миграции
      ↓
расчёт checksum
      ↓
поиск версии в schema_migrations
```

Если версия отсутствует:

```text
применить
```

Если версия существует и checksum совпадает:

```text
пропустить
```

Если версия существует, но checksum отличается:

```text
ERROR
```

Нельзя автоматически принимать изменённую историческую миграцию.

---

# 6. Migration Runner

Необходим отдельный механизм запуска миграций.

Целевой процесс:

```text
KuKLA Server / Migration command
             ↓
       Migration Runner
             ↓
     schema_migrations
             ↓
         PostgreSQL
```

Runner должен:

1. подключаться к PostgreSQL;
2. получать список файлов миграций;
3. сортировать их по версии;
4. проверять историю;
5. проверять checksum;
6. применять только отсутствующие миграции;
7. записывать результат в `schema_migrations`;
8. завершаться с ошибкой при нарушении последовательности.

---

# 7. Запуск миграций

Миграции не должны выполняться скрыто при каждом запуске приложения.

Предпочтительная модель:

```text
docker compose
      ↓
migration command
      ↓
database updated
      ↓
server start
```

Это позволит явно контролировать изменение схемы.

---

# 8. Транзакционность

По возможности каждая миграция выполняется в транзакции:

```text
BEGIN
   ↓
DDL / data migration
   ↓
schema_migrations INSERT
   ↓
COMMIT
```

При ошибке:

```text
ROLLBACK
```

Это особенно важно для миграций, которые изменяют несколько связанных сущностей.

Операции, которые невозможно выполнить внутри PostgreSQL-транзакции, должны быть отдельно документированы.

# 11. 006 — GIS

Цель:

перевести KuKLA от:

```text
lat
lng

```

к:

```text
PostGIS
```

Предпочтительные типы:

```text
geometry(Point, 4326)

geometry(Polygon, 4326)
geometry(MultiPolygon, 4326)
```

Необходимо добавить пространственные индексы:

```text
GiST
```

---

# 12. Миграция GIS

GIS-миграция должна использовать безопасную стратегию:

```text
ADD
 ↓
BACKFILL
 ↓
VERIFY
 ↓
APPLICATION MIGRATION
 ↓
DEPRECATE
 ↓
REMOVE
```

Нельзя одновременно:

```text
добавить geometry
+
удалить lat/lng
```

Сначала должна существовать совместимость.

---

# 13. Проверка GIS backfill

До миграции:

```text
points_old = N
```

После заполнения новой колонки:

```text
points_new = N
invalid = 0
```

Для каждой категории геометрий должны быть свои проверки.

# 14. 007 — GPS и треки

Следующая миграция:

```text
007_tracks_and_gps.sql
```

Цель:

отделить логический трек от отдельных GPS-точек.

Целевая модель:

```text
tracks
   ↓

```

GPS-точка должна иметь возможность однозначно определяться через:

* `search_id`;
* `user_id`;
* `device_id`;
* `track_id`;
* `client_point_id`;
* `sequence_number`;
* `recorded_at`;
* `received_at`.

---

# 15. Защита от дублей GPS

После восстановления связи мобильный клиент может повторно отправить уже переданные точки.

Поэтому должна существовать idempotency-граница.

Например:

```text
(device_id, client_point_id)
        ↓
      UNIQUE
```

Повторная передача той же точки не должна создавать новую запись.

# 16. 008 — Sync Hardening

Миграция:

```text

```

Цель:

сделать offline-first синхронизацию устойчивой к:

* конфликтам;

Целевой поток:

```text

  ↓
SENT
  ↓
SERVER
  ↓

  ↓

  ↓

  ↓

```

# 17. 009 — Permissions

Миграция:

```text
009_permissions.sql
```

Цель:

перейти от только глобальных ролей к модели:

```text
Role
  +
Permission
```

Целевые сущности:

```text

```

Существующие роли KuKLA сохраняются.

Миграция должна быть additive и не должна ломать существующий RBAC.

# 23. Expand / Migrate / Contract

Для потенциально опасных изменений применяется стратегия:

## Expand

Добавляем новую структуру.

```text
old + new
```

## Migrate

Приложение начинает работать с новой структурой.

```text
new
```

## Verify

Проверяем соответствие данных.

## Contract

Удаляем старую структуру.

```text
new only
```

Это предпочтительнее одномоментных разрушительных изменений.

# 25. Проверка upgrade

Отдельно проверяется обновление существующей БД:

```text
старое состояние
      ↓
backup
      ↓
migration runner
      ↓
новая схема
      ↓
verification
```

Проверяются:

* количество строк;
* внешние ключи;
* уникальность;
* индексы;
* значения критических полей;
* связи;
* API;
* синхронизация.

---

# 26. Backup перед production migration

Перед изменением production БД:

```text
BACKUP
   ↓
PREFLIGHT
   ↓
MIGRATION
   ↓
VERIFY
   ↓
MONITOR
```

Для критических миграций должен существовать проверенный план восстановления.

---

# 27. Что запрещено

Migration runner не должен:

* удалять данные автоматически;
* очищать таблицы ради успешного запуска;
* пересоздавать production БД;
* молча игнорировать ошибки;
* выполнять старую миграцию повторно;
* принимать изменённую миграцию с несовпадающим checksum;
* скрывать ошибки миграции от оператора.

# 30. Definition of Done

Миграция считается завершённой, если:

* успешно запускается на чистой БД;
* успешно обновляет существующую БД;
* не теряет данные;
* имеет checksum;
* проходит проверки целостности;
* совместима с backend;
* не нарушает RBAC;
* не нарушает организационную изоляцию;
* не нарушает GPS;
* не нарушает синхронизацию;
* имеет процедуру восстановления;
* документирована.

# 32. Главный принцип

> **Сначала создаём механизм безопасного изменения схемы, затем начинаем изменять саму схему.**

KuKLA должна уметь пройти путь:

```text
существующая БД
      ↓
migration runner
      ↓
новые миграции
      ↓
новая схема
      ↓
те же данные
      ↓
проверенная работа приложения
```

без потери истории поисковых операций.
