# Тест KuKLA в домашней сети с TrueNAS SCALE

**Это экспериментальный вариант для теста, не для эксплуатации.** Он не предназначен для реальных поисков и персональных данных. Он не настраивает интернет-доступ. Операции Windows-прототипа остаются локальными и не синхронизируются с сервером. Не запускайте этот набор команд непосредственно в оболочке хоста TrueNAS: предполагается отдельная тестовая Linux-VM с Docker Compose v2. На компьютере с 6 ГБ памяти и старым двухъядерным процессором VM может работать медленно или оказаться непригодной; до создания VM проверьте виртуализацию, свободные ресурсы и состояние пула. Не изменяйте существующие пулы или их настройки ради теста.

## До запуска

1. Используйте только вымышленные тестовые записи. Убедитесь, что на роутере **нет переадресации порта 18443** к VM, а доступ ограничен доверенной домашней сетью. Не открывайте PostgreSQL и панель TrueNAS наружу. Проверьте ограничения локального межсетевого экрана; привязка к LAN-адресу сама по себе не защищает от доступа участников этой сети или уже настроенного проброса порта.
2. Подготовьте отдельную Linux-VM с Docker Engine, Compose v2, `git`, `openssl`, Python 3 и доступом к интернету для загрузки образов и сборки. У неё должен быть собственный RFC1918 IPv4 в той же сети, что Windows-компьютер; **это не адрес панели TrueNAS**. Как именно создать и подключить VM, зависит от версии TrueNAS и её сетевой конфигурации. Не использовать нестабильную версию системы для ответственной эксплуатации.
3. На VM склонируйте проверенную ветку репозитория в домашнюю папку. В примере ниже приведена текущая экспериментальная ветка — если её нет, нужен соответствующий проверенный коммит:

   ```sh
   cd ~
   git clone --branch arena/d7b29bbf-kukla https://github.com/kuz55/KuKLA.git
   cd KuKLA/infrastructure/lan-test
   ```

## Создать тестовые секреты и запустить

Узнайте назначенный VM IPv4, например командой `ip -4 addr`. Вместо примера ниже укажите **реальный адрес VM**, например `192.168.0.90`, если именно он ей назначен. Не вводите публичный IP, пароль или адрес TrueNAS. Убедитесь, что порт 18443 на этом адресе свободен.

```sh
./init-test.sh 192.168.0.90
# Сохраните показанный SHA-256 сертификата для проверки копии.
docker compose -f compose.yml up -d --build
# Посмотреть состояние:
docker compose -f compose.yml ps
```

Скрипт создаёт `.env` и папку `private` с тестовым центром сертификации и серверным сертификатом на 30 дней. Он не перезаписывает существующую конфигурацию. Не отправляйте никому `.env`, закрытые ключи или вывод конфигурации с секретами. Этот тестовый центр сертификации нельзя использовать в production. Если адрес VM изменится, сертификат нужно перевыпустить; не делайте это поверх существующей конфигурации без плана сохранения базы и секретов.

Проверка с VM (подставьте тот же IP):

```sh
curl --fail --cacert private/test-ca.crt https://192.168.0.90:18443/ready
./bootstrap-test-owner.sh
```

Вторая команда интерактивно создаёт тестового владельца после завершения миграций. Используйте вымышленные имя и email и отдельный тестовый пароль не короче 12 символов. Пароль не нужно присылать в чат. Если `/ready` не отвечает, проверьте `docker compose -f compose.yml ps` и журналы; не размещайте журналы или секреты в публичном доступе. Базовые регистрация и вход работают, но экспериментальные API приёма и координации в этом режиме намеренно отключены.

## Доверие сертификату только на тестовом Windows-пользователе

Установка собственного корневого сертификата расширяет доверие Windows: владелец его закрытого ключа может выпускать сертификаты, которым этот пользователь будет доверять. Устанавливайте его только на выделенном тестовом компьютере/пользователе, если понимаете этот риск. Храните ключ только на VM, никому его не передавайте и удалите доверие после теста.

1. По доверенному каналу скопируйте на Windows **только** `private/test-ca.crt` (не `.key`, не `.env`). Сверьте SHA-256 файла, показанный при создании, с Windows PowerShell: `Get-FileHash .\test-ca.crt -Algorithm SHA256`. Значения должны совпасть. Не доверяйте сертификату при несовпадении.
2. В PowerShell от обычного пользователя, в папке с сертификатом, выполните:

   ```powershell
   Import-Certificate -FilePath .\test-ca.crt -CertStoreLocation Cert:\CurrentUser\Root
   ```

   Запишите отпечаток `Thumbprint` результата для удаления после испытания. Это изменяет хранилище доверия текущего пользователя Windows.
3. В тестовой сборке KuKLA откройте **Вход на сервер** и введите `https://192.168.0.90:18443`, подставив адрес VM, для которого создан сертификат. Введите тестовый email и пароль. После теста нажмите **Выйти**. При недоступном сервере клиент сообщает, что удалённое завершение сессии не подтверждено.
4. Удалите тестовый корневой сертификат после проверки: откройте `certmgr.msc` → **Доверенные корневые центры сертификации → Сертификаты**, найдите сертификат `KuKLA local test CA`, сравните отпечаток и удалите только его. При компрометации ключа немедленно удалите доверие. Не храните тестовый ключ в общедоступной папке.

## Остановка

На VM из каталога `infrastructure/lan-test`:

```sh
docker compose -f compose.yml down
```

Команда останавливает контейнеры, но **не удаляет том базы**. Не используйте `down -v`, пока не принято решение об удалении тестовой базы. Снимок или второй диск в том же устройстве не заменяет отдельную проверенную резервную копию.

## Статус проверки

Скрипт создания сертификата, конфигурация Compose и запуск тестового стека с входом проверяются в CI. Также пользователь провёл один локальный тест: Debian 13 в VM TrueNAS SCALE 28.0.0-MASTER, HTTPS `/ready` из VM и Windows, вход и выход в Windows GUI. Сертификат CA удалён из хранилища тестового пользователя Windows; контейнеры остановлены с сохранением тома базы. Результат относится только к указанному тесту, а не к работе с реальными данными, интернет-доступу, нагрузке или полному поисковому сценарию.

При этом ручном тесте пакеты Debian `docker.io` содержали Buildx 0.13, недостаточный для Compose 2.40.3; Compose 2.40.3 и Buildx 0.24.0 были установлены вручную. Они **не обновляются** менеджером пакетов Debian. При использовании Docker через sudo команды Compose и bootstrap тоже требуют sudo. На Windows curl со Schannel не смог проверить статус отзыва временного CA: тест `/ready` прошёл с `--ssl-no-revoke` только для отдельной команды, но GUI входил с обычной проверкой Windows. Не отключайте проверку сертификата приложения. Доверие к CA следует добавлять только для тестового пользователя после проверки отпечатка и удалять после теста.

Существующий общий PATCH поиска временно отклоняет изменение статуса: согласованные закрытие и повторное открытие ещё не реализованы. Операции приложения всё ещё локальные, не синхронизируются и не защищены серверной сессией. Остальные серверные права и процессы не завершены. Не использовать стенд для реальных поисков и персональных данных.
